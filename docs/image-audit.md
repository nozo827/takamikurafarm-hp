# 画像の調査結果

Web ページとして過大な画像がないかを調べた記録。

調査日: 2026-09-05

---

## 1. サマリ

ページを開いたときに読み込まれる画像の総量。

| ページ | 点数 | 総量 | 備考 |
|---|---|---|---|
| **`/`（トップ）** | 44 | **10.9MB** | 最も重い |
| **`/hurusato.html`** | 16 | **8.0MB** | |
| `/shop.html` | 12 | 2.9MB | |
| `/about.html`（和土滋味） | 17 | 1.1MB | Astro が最適化済み |
| `/news.html` | 6 | 0.7MB | |
| `/contact.html` | 5 | 0.3MB | |

一般に、1 ページあたりの画像は合計 1〜2MB 以内が目安とされる。
**トップページの 10.9MB は 5〜10 倍の水準**で、モバイル回線では表示までに
相当の時間がかかる。

---

## 2. 原因

**`public/` に置いた画像は Astro の最適化を通らず、そのまま配信される。**

旧サイトから移植した画像は `public/images/` にあるため、
撮影されたままの寸法・容量で配信されている。

一方 `src/assets/` の写真は Astro が WebP へ変換し、表示サイズに合わせて
縮小するため軽い。和土滋味ページが 1.1MB に収まっているのはこのため。

---

| ファイル | 容量 | 寸法 | 使用ページ |
|---|---|---|---|
| `banner6.png` | **3,112KB** | 3595×923 | ふるさと納税 |
| `takamikura_signifiantsignifie_1.png` | 1,636KB | 2800×1200 | トップ |
| `hurusato1.jpg` | 997KB | 1307×1227 | ふるさと納税 |
| `takamikura3.png` | 967KB | 1192×512 | STORE LIST |
| `hurusato5.jpg` | 908KB | **4366×2463** | ふるさと納税 |
| `hurusato2.jpg` | 905KB | 1535×1518 | ふるさと納税 |
| `slideshow4.jpg` | 905KB | 1920×629 | トップ |
| `hurusato4.jpg` | 902KB | 2129×2000 | ふるさと納税 |
| `takamikura4.png` | 874KB | 1074×1200 | STORE LIST |
| `slideshow2.jpg` | 822KB | 1920×629 | トップ |

問題は 2 種類ある。

**① 寸法が大きすぎる**
`hurusato5.jpg` は 4366×2463 で、4K ディスプレイでも表示に使われない解像度。
ブラウザが縮小して表示するだけで、転送量が無駄になっている。

**② 写真を PNG で保存している**
`banner6.png` `takamikura3.png` などは写真・グラデーションを含む画像だが
PNG で保存されている。PNG は写真の圧縮に向かず、JPEG や WebP の
10〜30 倍の容量になる。

---

## 4. 改善の見込み（実測値）

`sharp`（Astro に同梱）で「幅 1920px に縮小 ＋ JPEG 品質 85」を試した結果。

| ファイル | 現在 | 変換後 | 削減 |
|---|---|---|---|
| `banner6.png` | 3,112KB | 92KB | **-97%** |
| `takamikura3.png` | 967KB | 114KB | -88% |
| `takamikura_signifiantsignifie_1.png` | 1,636KB | 226KB | -86% |
| `slideshow4.jpg` | 905KB | 189KB | -79% |
| `hurusato1.jpg` | 997KB | 305KB | -69% |
| `hurusato5.jpg` | 908KB | 443KB | -51% |
| **合計** | **8,524KB** | **1,369KB** | **-84%** |

この比率がおおむね全体に当てはまるとすれば、
**トップページは 10.9MB → 2MB 前後、ふるさと納税は 8.0MB → 1.5MB 前後**まで
下がる見込み。

WebP に変換すればさらに 2〜3 割小さくできるが、
`.jpg` のまま差し替えれば HTML を一切書き換えずに済む。

## 5. 配信されているが使われていない画像

`public/images/` の 147 点のうち、**72 点（27.1MB）はどのページからも参照されていない。**

| ファイル | 容量 |
|---|---|
| `home19.JPG` | 4,198KB |
| `home7.jpg` | 1,553KB |
| `takamikura_signifiantsignifie_2.png` | 1,445KB |
| `sakuduke.jpg` | 1,041KB |
| `20k_b.jpg` | 978KB |
| `10k.jpg` | 931KB |
| `about_top_sp.jpg` | 927KB |
| `mainimg6.jpg` | 927KB |

利用者がダウンロードするわけではないので表示速度には影響しないが、
リポジトリとデプロイの容量を押し上げている。

**ただし削除は慎重に。** 旧サイトの過去ページで使われていた可能性や、
外部から直接リンクされている可能性がある。判断がつくまでは残すのが安全。

## 6. その他

### お知らせのサンプル画像が最適化されていない

`/about.html` と `/news.html` が読み込む `DSC07783`（386KB）は、
JPEG のまま配信されている。`src/data/site.ts` の `newsFallback` で
`newsSampleImage.src`（画像のパスだけ）を渡しており、Astro の `<Image>`
コンポーネントを経由していないため、最適化の対象外になっている。

`<Image>` を通すか、`getImage()` で変換すれば WebP になる。

### ファビコン

`images/fav.png` は 245×259 / 85KB で、全ページで読み込まれる。
ブラウザが強くキャッシュするため実害は小さいが、
32×32 と 180×180 を書き出せば数 KB に収まる。

---

## 7. 対応案

影響と手間の順に並べると次のとおり。

1. **使用中の画像を一括で縮小・再圧縮する**（効果最大・HTML の変更不要）
   `public/images/` の画像を幅 1920px 上限で再保存する。
   元ファイルは別ディレクトリに退避しておく。
2. **`newsFallback` の画像を `<Image>` 経由にする**（386KB → 数十 KB）
3. **ファビコンを小さく書き出す**
4. **未参照の 72 点を整理する**（要判断）
